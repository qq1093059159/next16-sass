# 第 06 课 · 错误边界与 404 状态码

> **学习目标**：掌握错误边界的层级、`notFound()` 的行为，以及本仓库实测出的那个**极易踩坑**的状态码真相。
> **对应代码**：`app/(root)/error.tsx`、`app/global-error.tsx`、`app/(root)/notfound/`、`app/(root)/notfound-dynamic/`、`app/api/notfound/route.ts`
> **预计耗时**：45 分钟

## 一、错误边界的层级

Next.js 的错误边界是**就近生效**的：

```text
app/global-error.tsx      ← 兜底（根 layout 都救不回来时）
  app/(root)/error.tsx    ← (root) 路由组内
    app/basic/error.tsx   ← basic 段内
```

规则：

| 边界 | 捕获范围 | 客户端？ | 必须含 `<html><body>`？ |
|---|---|---|---|
| `error.tsx` | **同级及以下** | ✅ 是 | 否 |
| `global-error.tsx` | 整个应用 | ✅ 是 | ✅ **是** |
| `not-found.tsx` | 未匹配路由 + `notFound()` | 否 | 否 |

`error.tsx` 接两个 prop：

```tsx
{ error, reset }: {
  error: Error & { digest?: string };
  reset: () => void;
}
```

- `error` —— 服务端抛出的错误对象。服务端错误会带 `digest` 哈希（**不泄露堆栈**，这是安全设计）。
- `reset` —— 重新渲染这一段的回调。

## 二、`notFound()` 的作用

`notFound()` 会终止当前渲染，渲染最近层级的 `not-found.tsx`。

```tsx
import { notFound } from "next/navigation";

export default async function Page() {
  const post = await getPost(id);
  if (!post) {
    notFound();          // ← 终止渲染，走 404 界面
  }
  return <div>{post.title}</div>;
}
```

和 `redirect()` 的区别：

| | 行为 | HTTP | URL |
|---|---|---|---|
| `redirect("/login")` | 跳走 | 307 | **会变** |
| `notFound()` | 显示 404 页 | 404（**但见下文**） | 不变 |

## 三、⚠️ 本仓库实测出的核心坑：PPR 下 `notFound()` 返回 200

这是本课**最重要**的内容，也是很多资料没讲清楚的。

### 3.1 实测数据

在干净的生产实例上（`pnpm build && pnpm start`）：

| 路由 | 构建产物形态 | HTTP 状态码 | 页面内容 |
|---|---|---|---|
| `/notfound` | `○ Static`（静态预渲染） | **200 OK** | 404 界面 |
| `/notfound-dynamic` | `◐` PPR 壳子（含 `await connection()`） | **200 OK** | 404 界面 |
| `/ssg/999`（数据不存在） | `◐` PPR 壳子 / ISR | **200 OK** | 404 界面 |
| `/no-such-route`（路由未匹配） | — | **404 Not Found** ✅ | 404 界面 |

复现命令：

```bash
curl -I http://127.0.0.1:3000/notfound
# HTTP/1.1 200 OK
# x-nextjs-cache: HIT
# Cache-Control: s-maxage=31536000

curl -I http://127.0.0.1:3000/no-such-route
# HTTP/1.1 404 Not Found
```

### 3.2 Next 官方的真实规则

- 响应**尚未开始流式输出**时调用 `notFound()` → 框架可以把状态码设成 **404**
- 响应**已经开始流式输出**（预渲染壳子 / PPR 壳子已随首字节发出）→ 状态码**锁定 200**，
  404 界面只能作为后续流内容追加进去

在 Cache Components（PPR）模式下，几乎所有页面路由都会先输出一个预渲染壳子，
所以**页面里的 `notFound()` 基本都会得到「200 + 404 界面」**。

### 3.3 ⚠️ 常见误解：加 `connection()` 救不回来

很多人以为「先 `await connection()` 再 `notFound()`」就能拿到 404。
**实测不行** —— `/notfound-dynamic` 依然是 200，响应头带 `x-nextjs-postponed: 1`
（PPR 壳子已经发出）。

### 3.4 真实代码

`app/(root)/notfound/page.tsx`：

```tsx
import { notFound } from "next/navigation";

/**
 * 【坑点 A】静态预渲染路由里调用 notFound()。
 *
 * 实测（干净的生产实例，curl -I）：
 *   HTTP/1.1 200 OK
 *   x-nextjs-cache: HIT
 *   Cache-Control: s-maxage=31536000
 *
 * 现象：页面【看起来】是 404 界面，但 HTTP 状态码是 200。
 * 原因：整条路由在构建期就被预渲染成了静态产物，404 界面被固化进这个产物，
 *      于是它以「一个正常的缓存页面」被返回 —— 搜索引擎会把它当正常页收录。
 *
 * 对照组：/notfound-dynamic（加了 connection() 也仍然是 200，原因见该页）
 */
export default function NotFoundStaticDemo() {
  // 构建期就能确定「内容不存在」→ 构建期就抛出 404
  const postId = "";

  if (!postId) {
    notFound();
  }

  return <div>永远不会渲染到这里</div>;
}
```

`app/(root)/notfound-dynamic/page.tsx`：

```tsx
import { connection } from "next/server";
import { notFound } from "next/navigation";

/**
 * 【坑点 B】加了 connection() 之后，状态码【依然】是 200。
 *
 * 实测（干净的生产实例，curl -I）：
 *   HTTP/1.1 200 OK
 *   x-nextjs-prerender: 1
 *   x-nextjs-postponed: 1     ← PPR 壳子已随首字节发出
 *
 * 很多人以为「先 await connection() 再 notFound()」就能拿到 404 —— 不能。
 *
 * 真正的规则（Next 官方口径）：
 *   - 响应【尚未开始流式输出】时调用 notFound() → 框架可以把状态码设成 404；
 *   - 响应【已经开始流式输出】（预渲染壳子 / PPR 壳子已发出）→ 状态码锁定 200，
 *     404 界面只能作为后续流内容追加进去。
 *
 * ✅ 唯一稳定拿到 404 的场景：框架级「路由未匹配」
 * ✅ 依赖状态码的业务场景：在 Route Handler 里显式返回 404（见 app/api/notfound/route.ts）
 */
export default async function NotFoundDynamicDemo() {
  // 声明动态渲染：让这一段等真实请求来了再算
  await connection();

  // 模拟：查数据库后发现记录不存在
  const postId = "999";

  if (postId === "999") {
    notFound();
  }

  return <div>永远不会渲染到这里</div>;
}
```

### 3.5 ✅ 正确做法：Route Handler 显式返回 404

`app/api/notfound/route.ts`：

```ts
/**
 * Route Handler 里显式返回 404 —— 依赖 HTTP 状态码时的正确做法。
 *
 * 页面里的 notFound() 在 PPR 模式下往往只能给你「200 + 404 界面」，
 * 而 Route Handler 是自己写 Response，状态码由你说了算。
 */
export async function GET() {
  return new Response(
    JSON.stringify({ error: "NOT_FOUND", message: "该资源不存在" }),
    {
      status: 404,
      headers: { "Content-Type": "application/json; charset=utf-8" },
    },
  );
}
```

实测：`curl -I http://127.0.0.1:3000/api/notfound` → **404 Not Found** ✅

## 四、动手实验

### 实验 1：确认 404 界面与状态码不一致

```bash
pnpm build && pnpm start

curl -I http://127.0.0.1:3000/notfound
curl -s http://127.0.0.1:3000/notfound | grep -o "页面不存在"
```

**预期**：状态码 200，但页面内容是「页面不存在」。

### 实验 2：确认 connection() 救不回来

```bash
curl -I http://127.0.0.1:3000/notfound-dynamic
```

**预期**：还是 200，响应头里有 `x-nextjs-postponed: 1`。

### 实验 3：确认框架级 404 是对的

```bash
curl -I http://127.0.0.1:3000/no-such-route
```

**预期**：404 ✅

### 实验 4：确认 Route Handler 能自己控制状态码

```bash
curl -I http://127.0.0.1:3000/api/notfound
```

**预期**：404 ✅，body 是 JSON。

### 实验 5：触发真正的错误边界

打开 `app/basic/a/page.tsx`，把 `// throw new Error("错误");` 的注释去掉，

**预期**：显示 `app/basic/error.tsx` 的界面，含错误信息和「重试」按钮。
**状态码是 500**（这是真正的错误，不是 404）。

### 实验 6：验证错误边界的就近原则

把 `throw` 挪到 `app/(root)/about/page.tsx`（那文件里有一行注释掉的 `throw`），
再访问 <http://localhost:3000/about>。

**预期**：命中 `app/(root)/error.tsx`（显示「段级错误边界」+ 错误信息），
而不是 basic 的那个。

## 五、常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 以为 `notFound()` 一定返回 404 | 搜索引擎收录大量「伪 200」的 404 页 | 依赖状态码就用 Route Handler |
| 以为加 `connection()` 就能修 | 白忙一场 | PPR 壳子已发出就改不了状态码 |
| `error.tsx` 不接 `error`/`reset` | 拿不到错误、无法重试 | 两个 prop 都接 |
| `global-error.tsx` 缺 `<html><body>` | 触发时整页白屏 | 自己补上 |
| 服务端错误直接把堆栈吐给客户端 | 信息泄露 | 生产环境用 `error.digest` 关联服务端日志 |

## 七、小结 & 下一步
