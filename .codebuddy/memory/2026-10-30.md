## 任务：MDX 插件是否支持「目录即内容源」→ 实现了一套完整方案

### 结论（回答用户的问题）

**`@next/mdx` 本身不做目录扫描。** 它是**编译期 loader**，把 `.mdx` 编译成 React 组件，
配合 `pageExtensions` 纳入 Next 的**文件式路由** —— 遵循「一个文件 = 一个路由」。
它**不**做：① 扫描任意目录生成列表页；② 解析 YAML frontmatter；③ 支持 `app/` 之外的目录。

### 本轮实现（模式 B：动态路由 + 目录扫描）

```
content/hello.mdx          ← .mdx（支持 JSX）+ 自定义组件
content/pure-markdown.md   ← 纯 .md
lib/posts.ts               ← 扫描目录 + 动态 import
app/posts/page.tsx         ← 列表页（自动生成）
app/posts/[slug]/page.tsx  ← 详情页 + generateStaticParams
components/mdx/Callout.tsx ← MDX 自定义组件
mdx-components.tsx         ← 组件映射表（接管 h1/h2/a + 登记 Callout）
```

- `next.config.ts`：启用 `createMDX({ extension: /\.(md|mdx)$/ })` + `pageExtensions` 加 md/mdx
- `app/globals.css`：补 `@plugin "@tailwindcss/typography"`（v4 引插件方式，v3 是写进 config）
- 元数据用 **MDX 原生的 `export const metadata`**（ESM 导出），**不用 YAML frontmatter**（默认不支持）

### 三个实测坑（都已写进文档）

1. **动态 import 的 key 必须是「含扩展名的完整文件名」** ——
   写死 `.mdx` 会导致 `.md` 文件找不到（`Cannot find module '@/content/pure-markdown.mdx'`）。
   原因：动态 import 表达式被编译成「目录下所有匹配扩展名文件」的 context map，key 是完整路径。
   → `lib/posts.ts` 因此同时返回 `slug`（给 URL）和 `file`（给 import）。
2. **必须用 `@/` 别名，不能用相对路径** —— 列表页(`app/posts/`)与详情页(`app/posts/[slug]/`)
   到根的相对深度不同，同一表达式指向不同位置。
3. **加文章必须重新 build** —— 目录扫描在构建期（`generateStaticParams` + `fs.readdirSync`）。
   想「加完即见」：`await connection()`（变动态）或 `"use cache"` + `cacheTag` + `revalidateTag`。

附带印证第 06 课的坑：`/posts/not-exist` 返回 **200**（`◐` PPR 壳子，状态码已锁定）。

## 追加任务：把博客基础架构升级为「多分类目录」

用户追问：「多建立几个分类目录，每个分类放 .md/.mdx，能自动解析吗？」

### 升级前先实测出两个「不能」

1. **分类子目录里的文章被完全忽略** —— 原实现 `fs.readdirSync(POSTS_DIR)` 不递归。
   改成 `{ recursive: true }` 后又踩到 **Windows 反斜杠**坑：
   `readdirSync(recursive)` 在 Windows 返回 `tech\nested-post.mdx`（反斜杠），
   拼出的 import key 与 context map 对不上 → `Cannot find module '@/content/tech\nested-post.mdx'`。
   修复：`.map((file) => file.split(path.sep).join("/"))`。
2. **`.md` 文件不支持 `export const metadata`** —— 实测 `.md` 走**纯 CommonMark**，
   ESM 导出会被**当正文原样渲染出来**（构建不报错！），标题退化成文件名。
   `.md` 里的 JSX 同理被当普通文本。
   原因：Next 对 `.md`/`.mdx` 用不同 loader 配置（`format:'md'` vs `'mdx'`），
   `@next/mdx` 的 `extension` 只控制「哪些文件走 loader」，改不了「用哪种语法解析」。
   **解法：同名 `.json` 旁路**（`reading-notes.md` ↔ `reading-notes.json`），旁路优先于 ESM export。

### 升级内容

- `lib/posts.ts`：递归扫描 + 分类推导 + `_meta.json`（分类名/描述）+ `.json` 旁路元数据（合并优先级：旁路 > ESM export）+ `getCategoryMeta()`
- `app/posts/[slug]/` → `app/posts/[...slug]/`：**catch-all 才能接住多段路径**（`/posts/tech/post`），
  `params.slug` 改成 `string[]`，`generateStaticParams` 返回 `{ slug: p.slugParts }`
- `app/category/[category]/page.tsx`：**分类零配置**，由 content 子目录名自动推导
- `app/posts/page.tsx`：加分类导航 + 分类徽标
- 修复 bug：详情页原本直接用 `import()` 出来的 metadata，漏掉 `.json` 旁路 → 改为走 `getPostMeta()`
- 示例：content/tech/{_meta.json,nested-post.mdx,ssg-deep-dive.mdx}、content/life/{_meta.json,reading-notes.md,reading-notes.json}

### 本轮实际补齐：unified 插件链

之前仓库**一个 remark/rehype 插件都没有**（表格/删除线/任务列表/代码高亮全无）。

**两个 Turbopack 下的实测坑**：

1. **插件必须用字符串包名** —— 传函数报
   `does not have serializable options`。Next 官方文档明确要求用字符串。
2. **`remark-mdx-frontmatter` 的 `name` 不能填 `metadata`** —— 该插件无条件注入导出，
   没有 frontmatter 的文件也会生成 `export const metadata = {}`，
   与手写同名导出撞名 → `Variable name conflict: metadata`。
   解法：`name: 'frontmatter'`，合并优先级交给 `lib/posts.ts` 的 `getPostMeta()`。

### ⚠️ 结论修正（重要）

**早先的结论「`.md` 不支持 ESM 导出 → 必须用同名 `.json` 旁路」被插件链实测推翻。**
准确的分层是：

| 层次 | 能力 | `.md` | `.mdx` |
|---|---|---|---|
| MDX 语法层 | JSX、手写 `export const metadata` | ❌ | ✅ |
| remark 插件层 | YAML frontmatter、GFM 表格 | ✅ | ✅ |

frontmatter 属 **remark 插件层** → 在 Markdown→AST 之前就剥掉了，与扩展名无关。
所以 **`.md` 与 `.mdx` 都能用 YAML frontmatter**，这才是业界主流写法。
`.json` 旁路降级为可选补充机制（用于放编译链读不到的字段）。

### 追加任务四：多级分类 / 路径分页 / 全文搜索（最后三项）

**用户的关键提问**：「多级分类是不是要针对 .mdx/.md 文档自动生成 params 路由的路径？」

**结论**：路由层面**早就支持**，实测把文件丢进 `content/a/b/` 立刻生成 `/posts/a/b/deep-post`。
「目录结构 = URL 路径」这条规则在 **`generateStaticParams`** 这一步生效：
返回的 `slug` 数组长度 = 路径深度，catch-all `[...slug]` 为每一段都生成实际路径。
真正缺的是**分类页本身**的层级能力（`getCategories()` 原来只取路径第一段）。

1. **多级分类** —— `getCategories()` 返回所有层级节点
   （path/name/depth/parent/count/totalCount/children）；分类页 `[category]` → `[...category]`；
   加面包屑 + 子分类导航。`/category/a` 含子分类，`/category/a/b` 只含自己。
2. **路径分页** —— `/posts/page/2`（不是 `?page=2`）。理由：路径分页是**静态生成**、
   每页独立 URL（SEO 友好）；query 参数要 `await connection()` 变动态。
   `generateStaticParams` **可以是 async** → `await getPostPage(1)` 精确得到总页数，
   比「保守估计 50 页」好（不生成一堆 404 路由）。从第 2 页开始（第 1 页就是 /posts）。
   路由匹配不冲突：静态段 `page` 优先于 catch-all。
3. **全文搜索** —— `lib/search.ts` 构建期算索引（读源文件用 gray-matter 剥 frontmatter，
   再用 markdownToPlainText 剥标记得到正文纯文本），直接内联进 `/search` 传给客户端组件，
   零额外请求。**★ 关键认知：Fuse.js 的编辑距离对中文无效**（无空格分词，
   「缓存」与「缓存机制」距离很大）→ 主路径是**子串匹配**（中文 100% 可靠），
   Fuse 只负责英文容错。索引体积 20KB / 12 篇。

导航栏原来是个静态的 `<p>Global Search</p>`，顺手改成真链接（并同步 doc/07 的代码块）。

新增依赖：`fuse.js@7.5.0`。
文档：README §11.12、doc/26 §十一（1225 行）、knowledge-map +4 知识点。

## 追加任务：修复 hydration mismatch + 弃用 next-themes（零依赖主题切换）

用户报错：`A tree hydrated but some attributes of the server rendered HTML didn't match`
（`<html>` 上服务端渲染 `class="light"` / `style="color-scheme:light"`，客户端是 dark）。
并要求「不用 next-themes，只用 shadcn/ui 或 tailwind 的亮暗切换」，**两个项目都要改**。

### 根因

next-themes 的 ThemeProvider 在**客户端**给 `<html>` 打 `class="light|dark"` 与
`style.color-scheme`，而服务端渲染时读不到 localStorage，只能假定一个值 → 属性不一致。

### 新方案（零第三方依赖，三层机制）

1. CSS 层：`:root` / `.dark` 两套 CSS 变量 + `@custom-variant dark (&:is(.dark *))`
2. JS 层：`applyTheme()` → `classList.toggle("dark")` + `style.colorScheme`
   + `data-theme`（解析后）+ `data-theme-pref`（原始偏好）
3. 时机层：`<head>` 内联脚本（hydration 之前执行）→ 首屏无闪烁

### 三条关键工程决策（本轮最有价值的沉淀）

1. **图标不用 React state 控制** —— 服务端读不到 localStorage，客户端首帧才知道。
   `useState` 与 `useSyncExternalStore` **都会 mismatch**（后者 `getSnapshot`
   在首次 hydration 就返回真实值）。解法：**双图标都在 DOM，靠 CSS 的
   `scale/rotate` 切换显隐** → HTML 服务端与客户端完全一致。
2. **三态菜单不用 `DropdownMenuRadioGroup`**（那也需要 state）→ 普通
   `DropdownMenuItem` + CSS 画的 ✓，规则由
   `:root[data-theme=…]` / `[data-theme-pref=…]` 选择器决定。
3. **防闪脚本必须内联在 `<head>`** —— `next/script` 异步加载会闪一帧。
   `<html>` 必须保留 `suppressHydrationWarning`（只压制 `<html>` 自身属性）。

### 实测踩到的三个坑

1. **dev 用 `127.0.0.1` 访问 → React 根本不 hydrate**（沙箱里实测到）。
   Next 拦截跨域 dev 资源 → 客户端 chunk 被拦 → 页面所有交互失效，
   **控制台除一行 warning 外无任何报错**。解法：用 `localhost` 或配
   `allowedDevOrigins`。排查手段：
   `Object.keys(document.querySelector('button')).filter(k=>k.startsWith('__react'))`
   为空 = 未 hydrate。
2. **`@media (prefers-color-scheme: dark)` 驱动的 CSS 变量，class 切换对它无效** ——
   web/ 原本就是这么写的（只能跟随系统）。已改为 `.dark` 类驱动。
3. **eslint-config-next v16 与旧 FlatCompat 写法不兼容** —— web/ 报
   `Cannot find package '@eslint/eslintrc'`。改为 Next 16 的扁平配置：
   `import nextVitals from "eslint-config-next/core-web-vitals"` + `defineConfig`。

## 追加修复：Blocking Route 报错（params 必须在 Suspense 内读取）

用户报错：`Route "/tags/[tag]": Next.js encountered runtime data during prerendering.`

### 根因

`cacheComponents`（PPR）要求页面能预渲染成静态壳，而 `params` / `searchParams` /
`cookies()` / `headers()` 是**运行时数据** —— 在 `<Suspense>` 外读它们，
Next 无法确定静态壳长什么样 → 整条路由降级为 blocking → 报错。

### ⚠️ 最迷惑的点（务必记住）

**build 能过、dev 才报错**。因为 `generateStaticParams` 列出的参数可静态化，
但 **dev 模式还要渲染「任意参数」的兜底版本** → 那就得读运行时 params → 触发 blocking。
→ 验证必须访问一个 **`generateStaticParams` 里没有的参数**（如 `/tags/zzz`），
   只访问枚举内的参数（`/tags/教程`）**测不出来**。

### 修法（官方写法）

页面组件**不 await params**，只把 Promise 往下传；真正 await 的 async 子组件放进 `<Suspense>`：

```tsx
export default function TagPage({ params }: { params: Promise<{ tag: string }> }) {
  return (
    <div className="mx-auto max-w-2xl p-6">
      <Suspense fallback={<TagSkeleton />}>
        <TagContent params={params} />
      </Suspense>
    </div>
  );
}
async function TagContent({ params }: { params: Promise<{ tag: string }> }) {
  const { tag } = await params;   // ← 在 Suspense 内部才 await
}
```

另一种修法：`export const instant = false;`（整条路由 blocking，失去预渲染）。

### ⚠️ 副作用（必须知情）

加 Suspense 后，**枚举外参数的 404 状态码会变成 200** —— PPR 壳子先流式输出，
状态码已锁定 200，后续追加的 404 界面改不了。与第 06 课同一个坑。
内容站通常取舍「软 404 换静态预渲染」。

## 追加：web 仓库架构评审（发现并修复一个 SEO 级 bug）

用户要求「全面介绍 web 仓库的优点不足、系统基座定位」。评审中做了实测，
**发现两个项目都存在一个 SEO 级 bug 并已修复**。

### 🐛 发现的 bug：文章页 <head> 的元数据全退化成文件名

构建产物实测（修复前）：
```
<title>hello · next16-sass</title>          ← 应为「第一篇文章：用 MDX 写博客」
<title>first-post · next16-sass</title>     ← 应为「新闻分类的第一篇」
<meta name="description">                  ← 缺失
<meta name="keywords">                     ← 缺失
<meta property="og:title" content="hello">
```

**根因**：MDX 有三条元数据来源 ——
① YAML frontmatter → 编译成 `export const frontmatter`
② 手写 `export const metadata` → Next 原生
③ 同名 `.json` 旁路 → 不在编译产物里

`generateMetadata` 里写的是 `const meta = mod.metadata ?? {}` → **只拿得到第 ② 条**。
示例文章全用 YAML frontmatter → 全部取不到。

⚠️ **页面正文显示正常**（正文走 `getPostMeta()`），**只有 `<head>` 是错的** ——
这类 bug 肉眼完全发现不了，最容易漏到线上。

**修法**：`generateMetadata` 改走 `getPostMeta(entry.slug)`，两个项目同步。
**自检命令**：`grep -oE "<title>[^<]*</title>" .next/server/app/posts/hello.html`

### 实测核实的结论（供后续评审复用）

- **dev 模式新增 .mdx 文章立即可见**（列表页 + 详情页都出内容），**不需要重新 build**。
  之前的疑虑不成立 —— 动态 import 的 context map 限制只在编译期成立，
  新增文件后 Turbopack 会重新编译，而运行时扫描本来就是实时的。
- **无缓存层**：全仓没有一处 `"use cache"` / `revalidateTag` / `cacheLife`（只在注释里提到）。
- **O(N²) 目录扫描**：`getAllPostMeta()` → 每篇 `getPostMeta()` → 每次都 `getPostFiles()`
  （readdirSync + 过滤 + 排序）→ N=500 篇时约 25 万次文件操作。
- **每篇文章 spawn 一次 git**：`getLastGitModified` 用 `execFileSync`（同步阻塞事件循环），
  500 篇 = 500 次进程创建，构建期多花 10~25 秒。
- **搜索索引构建期算好、全量内联进 HTML**（README 自己警告过：几百篇后建议改静态 JSON + fetch）。
- **OG 图走 `getPostMeta()`** ✓ 不受元数据 bug 影响。

### 评审结论摘要

优点：零框架绑定（16 个 runtime 依赖全是 remark/rehype/mdast）、目录即内容源的一致性、
静态优先 + PPR 流式、TOC 锚点 100% 一致（用 rehype-slug 同款 github-slugger 而非正则）、
中文优先的搜索策略、SEO 完整（含 llms.txt 与 AI 爬虫策略）、优雅降级。

不足：① 元数据 bug（已修）② O(N²) 扫描 ③ 每篇 spawn git ④ 搜索索引内联 ⑤ 无缓存层
⑥ 404 状态码 200 ⑦ frontmatter 无 schema 校验（字段名写错静默失效）
⑧ 缺 i18n / 版本化 / CMS / 预览 / 评论 / 重定向表。

定位：**内容层**（不是完整站点框架）—— 文章站/博客站/文档站的内容层，
零框架绑定是它最大的价值（两成缺口可按需嫁接）。
