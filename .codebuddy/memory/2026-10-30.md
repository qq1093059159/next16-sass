## 任务：MDX 插件是否支持「目录即内容源」→ 实现了一套完整方案

### 结论（回答用户的问题）

**`@next/mdx` 本身不做目录扫描。** 它是**编译期 loader**，把 `.mdx` 编译成 React 组件，
配合 `pageExtensions` 纳入 Next 的**文件式路由** —— 遵循「一个文件 = 一个路由」。
它**不**做：① 扫描任意目录生成列表页；② 解析 YAML frontmatter；③ 支持 `app/` 之外的目录。

### 本轮实现（模式 B：动态路由 + 目录扫描）

```
content/hello.mdx          ← .mdx（支持 JSX）+ 自定义组件
content/pure-markdown.md   ← 纯 .md
lib/posts.ts               ← 扫描目录 + 动态 import
app/posts/page.tsx         ← 列表页（自动生成）
app/posts/[slug]/page.tsx  ← 详情页 + generateStaticParams
components/mdx/Callout.tsx ← MDX 自定义组件
mdx-components.tsx         ← 组件映射表（接管 h1/h2/a + 登记 Callout）
```

- `next.config.ts`：启用 `createMDX({ extension: /\.(md|mdx)$/ })` + `pageExtensions` 加 md/mdx
- `app/globals.css`：补 `@plugin "@tailwindcss/typography"`（v4 引插件方式，v3 是写进 config）
- 元数据用 **MDX 原生的 `export const metadata`**（ESM 导出），**不用 YAML frontmatter**（默认不支持）

### 三个实测坑（都已写进文档）

1. **动态 import 的 key 必须是「含扩展名的完整文件名」** ——
   写死 `.mdx` 会导致 `.md` 文件找不到（`Cannot find module '@/content/pure-markdown.mdx'`）。
   原因：动态 import 表达式被编译成「目录下所有匹配扩展名文件」的 context map，key 是完整路径。
   → `lib/posts.ts` 因此同时返回 `slug`（给 URL）和 `file`（给 import）。
2. **必须用 `@/` 别名，不能用相对路径** —— 列表页(`app/posts/`)与详情页(`app/posts/[slug]/`)
   到根的相对深度不同，同一表达式指向不同位置。
3. **加文章必须重新 build** —— 目录扫描在构建期（`generateStaticParams` + `fs.readdirSync`）。
   想「加完即见」：`await connection()`（变动态）或 `"use cache"` + `cacheTag` + `revalidateTag`。

附带印证第 06 课的坑：`/posts/not-exist` 返回 **200**（`◐` PPR 壳子，状态码已锁定）。

## 追加任务：把博客基础架构升级为「多分类目录」

用户追问：「多建立几个分类目录，每个分类放 .md/.mdx，能自动解析吗？」

### 升级前先实测出两个「不能」

1. **分类子目录里的文章被完全忽略** —— 原实现 `fs.readdirSync(POSTS_DIR)` 不递归。
   改成 `{ recursive: true }` 后又踩到 **Windows 反斜杠**坑：
   `readdirSync(recursive)` 在 Windows 返回 `tech\nested-post.mdx`（反斜杠），
   拼出的 import key 与 context map 对不上 → `Cannot find module '@/content/tech\nested-post.mdx'`。
   修复：`.map((file) => file.split(path.sep).join("/"))`。
2. **`.md` 文件不支持 `export const metadata`** —— 实测 `.md` 走**纯 CommonMark**，
   ESM 导出会被**当正文原样渲染出来**（构建不报错！），标题退化成文件名。
   `.md` 里的 JSX 同理被当普通文本。
   原因：Next 对 `.md`/`.mdx` 用不同 loader 配置（`format:'md'` vs `'mdx'`），
   `@next/mdx` 的 `extension` 只控制「哪些文件走 loader」，改不了「用哪种语法解析」。
   **解法：同名 `.json` 旁路**（`reading-notes.md` ↔ `reading-notes.json`），旁路优先于 ESM export。

### 升级内容

- `lib/posts.ts`：递归扫描 + 分类推导 + `_meta.json`（分类名/描述）+ `.json` 旁路元数据（合并优先级：旁路 > ESM export）+ `getCategoryMeta()`
- `app/posts/[slug]/` → `app/posts/[...slug]/`：**catch-all 才能接住多段路径**（`/posts/tech/post`），
  `params.slug` 改成 `string[]`，`generateStaticParams` 返回 `{ slug: p.slugParts }`
- `app/category/[category]/page.tsx`：**分类零配置**，由 content 子目录名自动推导
- `app/posts/page.tsx`：加分类导航 + 分类徽标
- 修复 bug：详情页原本直接用 `import()` 出来的 metadata，漏掉 `.json` 旁路 → 改为走 `getPostMeta()`
- 示例：content/tech/{_meta.json,nested-post.mdx,ssg-deep-dive.mdx}、content/life/{_meta.json,reading-notes.md,reading-notes.json}

## 追加任务二：调研业界解析 md 的主流做法 → 补齐插件链

### 业界现状（npm 实测 + 官方文档核实）

| 方案 | 代表 | 现状（2026-10） |
|---|---|---|
| 文件式路由 | `@next/mdx` | 活跃（npm 16.4.3） |
| 动态路由 + 文件扫描 | `fs.readdirSync` + 动态 `import()` | Next 官方 examples 做法，活跃 |
| 运行时编译 | `next-mdx-remote` / `-client` | 原版 6.0.0 已 archive（2026-02 停更），**改用 `next-mdx-remote-client`**（2.1.12 活跃） |
| 内容层 / 内容集合 | Contentlayer → **Velite** | **Contentlayer 已死**（2023-07 最后发布），Velite 0.4.0 活跃 |
| 文档站框架 | **Fumadocs** 16.17.9 / **Nextra** 4.6.1 | 活跃，版本号跟 Next 对齐 |
| 非 Next 生态 | Docusaurus / VitePress / Hugo | 各自活跃 |

关键认知差：**技术文档官网仓库里多是 .md 文件，但那个站点未必由 Next.js 驱动**
（Next.js 官方文档在 `vercel/next.js` 的 `docs/`，用的是自研工具链；Tailwind/Prisma 的文档站才是 Next+MDX）。

### 本轮实际补齐：unified 插件链

之前仓库**一个 remark/rehype 插件都没有**（表格/删除线/任务列表/代码高亮全无）。
已装并配置：`remark-gfm` `remark-frontmatter` `remark-mdx-frontmatter` `rehype-slug`
`rehype-pretty-code` `shiki` `gray-matter`。

**两个 Turbopack 下的实测坑**：

1. **插件必须用字符串包名** —— 传函数报
   `does not have serializable options`。Next 官方文档明确要求用字符串。
2. **`remark-mdx-frontmatter` 的 `name` 不能填 `metadata`** —— 该插件无条件注入导出，
   没有 frontmatter 的文件也会生成 `export const metadata = {}`，
   与手写同名导出撞名 → `Variable name conflict: metadata`。
   解法：`name: 'frontmatter'`，合并优先级交给 `lib/posts.ts` 的 `getPostMeta()`。

### ⚠️ 结论修正（重要）

**早先的结论「`.md` 不支持 ESM 导出 → 必须用同名 `.json` 旁路」被插件链实测推翻。**
准确的分层是：

| 层次 | 能力 | `.md` | `.mdx` |
|---|---|---|---|
| MDX 语法层 | JSX、手写 `export const metadata` | ❌ | ✅ |
| remark 插件层 | YAML frontmatter、GFM 表格 | ✅ | ✅ |

frontmatter 属 **remark 插件层** → 在 Markdown→AST 之前就剥掉了，与扩展名无关。
所以 **`.md` 与 `.mdx` 都能用 YAML frontmatter**，这才是业界主流写法。
`.json` 旁路降级为可选补充机制（用于放编译链读不到的字段）。
